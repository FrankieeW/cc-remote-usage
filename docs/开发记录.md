# 开发记录：ccr（cc-remote-usage）

把跑在服务器上的 Codex / Claude Code agent 的**今日用量**汇进 CC Switch 看板的完整来龙去脉。
记录的是「为什么这么做」和踩过的坑，代码结构见 README / AGENTS.md。

## 1. 需求

本机 CC Switch 的「用量」看板只统计本机 agent 的消耗；VPS 上跑的 agent（netcup、nuyek-yeats
等）看不到。目标是：**同一个看板里能看到所有服务器的今日/近 N 天用量**。

最早的误解是「要同步余额（额度）」，实测后发现用户要的是**每日消耗**，这是两条完全不同的数据通路。

## 2. 调研：CC Switch 的用量到底怎么来的

在 `~/.cc-switch/cc-switch.db` 里读出来的事实（CC Switch 4.0.16，Fleet 变体）：

| 表 | 字段/取值 | 含义 |
|---|---|---|
| `proxy_request_logs` | `data_source='proxy'` | 本机代理逐请求记账 |
| `proxy_request_logs` | `data_source='codex_session' / 'claude_session' / 'grok_session' / 'pi_session' / 'mcode_session'` | **从会话日志解析出来的用量** |
| `usage_daily_rollups` | `(date, app_type, provider_id, model, …)` | 按天汇总表 |
| `session_log_sync` | `file_path` 主键 + `last_byte_offset` | 增量游标，天然幂等 |
| `session_usage_dedup` | `(data_source, request_id)` | 会话用量去重 |

关键结论：

1. **「用量」= 会话日志解析**，入口是 `cc-switch sessions sync-usage`。
2. 扫描根受环境变量控制：`CODEX_HOME`（→ `$CODEX_HOME/sessions`、`$CODEX_HOME/archived_sessions`）、
   `CLAUDE_CONFIG_DIR`（→ `$CLAUDE_CONFIG_DIR/projects`）。
   ⇒ **把目录作用域化，就能只扫某台服务器的镜像目录**，这是整个方案的地基。
3. `session_log_sync` 按文件字节偏移去重，所以重复导入是安全的。
4. 会话解析出的用量统一归到伪供应商 `_codex_session` / `_session`，**不区分是哪台服务器**。
   ⇒ 按服务器拆分只能自己算（`ccr report`）。
5. `usage_daily_rollups` 在实测环境里 max(date) 停在旧日期，看板的近实时数据来自
   `proxy_request_logs`，别拿 rollups 当唯一事实源。

### 顺带查清的两件事

- **「额度」不是「用量」**：额度来自供应商的 `usage_script`（每个 provider 存
  `meta.usage_script` 的 JS，如 new-api 的 `/api/user/self`、MiniMax 的
  `/v1/api/openplatform/coding_plan/remains`），由 `cc-switch provider quota <id>` 触发。
  这条通路另有一个姊妹项目在做：[dsh-quota-bridge](../dsh-quota-bridge)
  （把 DSH 自己的额度显示进 CC Switch 卡片），附上游源码级调研。
- **服务器 agent 用的账号可能已经和本机同源**：逐台比对 key 指纹后发现 netcup 的 Claude
  用的是和本机 DeepSeek 相同的 key、frankie-vps 用同一个 MiniMax `sk-cp-` token、三台 Codex
  共用同一个 ChatGPT account（`044aff82…`）——这些本来就已经统一，只有 nuyek-yeats 是独立来源。

## 4. 技术选型与坑

1. **服务器普遍没装 rsync**（netcup 直接 `command not found`）⇒ 用 tar 流式：
   ```sh
   ssh host 'cd ~/.codex/sessions && find . -type f -name "*.jsonl" -newermt @N | tar -czf - -T -' \
     | tar xzf - -C <本地镜像目录>
   ```
   GNU tar 在文件列表为空时会产出**合法的空归档**并返回 0，所以管道不会报错——这点很重要，
   否则「今天没有新日志」会被当成失败。
2. **BSD find 不认 `-newermt @epoch`** ⇒ 远端先跑 `find . -maxdepth 0 -newermt '@0'`
   探测，失败就退回 `-mmin -N`。
3. **增量语义**：`find -newermt @<上次成功同步的 epoch>`；`last_epoch` **只在成功时推进**，
   失败不推进，避免漏数据。
4. **并发探测**：`std::thread::scope` + `AtomicUsize` 任务队列，固定 8 并发。12 台主机从
   串行的 ~40s 降到 7s。
5. **超时噪音**：完全不可达的主机每轮固定赔 5s 连接超时 ⇒ 指数退避（15m→30m→1h→2h→4h→6h，
   上限可配）。冷却中的主机在探测阶段就被剔除，连 SSH 连接都不建。
6. **Fleet 主机发现会混进 git 远端**：`cc-fleet hosts` 复用 Codex App 的 SSH 列表，里面包含
   `github.com` 的 git alias（`user git`）。必须先解析 `~/.ssh/config` 的
   `HostName`/`User`，反查过滤掉这些。
7. **计价口径**：读 CC Switch 自己的 `model-pricing.json`（不是 SQLite），模型名大小写不敏感、
   支持前缀匹配（带日期后缀的模型名），取最长命中；`codex-auto-review` 这类没有定价的记 `n/a`。
8. **时区**：会话 JSONL 里的时间戳是 UTC，`report` 转本地时区后归日；晚上 23:40 的会话会算到
   「昨天」，这是正确但容易误判的行为（本地日期 00:00 起算）。
9. **离线构建**：本机访问 crates.io 403，`cargo build --offline` 靠本地 registry 缓存
   （clap 4.6.7 / serde_json / dialoguer / chrono 都有），30 秒出 1.1MB 二进制。
10. **不要直接写 CC Switch 数据库**：所有数据都通过它自己的 CLI 落库，保持它的事务/去重逻辑。

## 5. 验证方法（可复用）

```sh
# 1) 看板数据源里各来源的条数
sqlite3 ~/.cc-switch/cc-switch.db \
  "select data_source, count(*) from proxy_request_logs group by 1 order by 2 desc"

# 2) 单台导入是否生效（作用域化环境变量）
CODEX_HOME=~/.cc-switch/remote-usage/<host>/codex \
CLAUDE_CONFIG_DIR=~/.cc-switch/remote-usage/<host>/claude \
  cc-switch sessions sync-usage --all --json

# 3) 自己的报告与看板数字对照
ccr report --days 2

# 4) 验证幂等：连跑两次，第二轮 imported 应为 0
ccr sync <host>

# 5) 验证导入作用域：filesScanned 应等于该主机镜像里的 .jsonl 数，大出来说明扫到了本机其他 app
find ~/.cc-switch/remote-usage/<host> -name '*.jsonl' | wc -l
```

远端脚本的可移植性不用连服务器验证：`cargo test` 会在本机用 `sh` 直接跑探测 / 拉取脚本
（macOS 上即 BSD find / wc / du / bsdtar）。注意 Claude Code 的交互 shell 把 `find` 包成了 bfs，
手工验证 BSD 行为要用 `/usr/bin/find` 或 `sh -c`。

实测基线（2026-10-21）：

- netcup：3 天 41 个 Codex rollout ≈ 228MB 压缩后，首次 3 分钟；增量 4.2 秒
- nuyek-yeats：2 天 17 个文件 56MB，首次 8 秒导入 1286 条
- 12 台并发探测 7.0s；5 台进入冷却后 2.9s

## 6. 已知局限

- 看板内不区分服务器（归到 `_codex_session`），要拆分看 `ccr report`。
- `$` 是按 `model-pricing.json` 折算的 token 成本，**不等于中转站账单**。
- 只支持 Linux / macOS + 公钥免密（`BatchMode=yes`）；远端要有 POSIX `sh`（登录 shell 是什么无所谓）。
- 活跃的大 rollout 每次被追加都会整份重拉（netcup 上有单个 190MB 的会话文件）。
- 依赖 agent 日志在默认位置（`~/.codex/sessions`、`~/.claude/projects`）。
- 时间戳与本地时区跨日时会话归属可能「差一天」，属预期。

## 7. 后续可做

- 探测成功但没日志的主机，`ccr status` 里仍挂着旧的失败原因，可在探测成功时清掉

## 9. v3：真实环境复盘（2026-10-21）

对着本机的 state.json、launchd 日志、CC Switch 数据库（只读）和两台在用服务器逐项核对后发现的问题。

| 问题 | 证据 | 处理 |
|---|---|---|
| 每台导入都顺带扫了本机其他 app | CC Switch 已是 5.11.2，`--all` 覆盖 7 个 app；netcup 镜像 41 个文件，`filesScanned` 却是 172 | 按 `--app codex` / `--app claude` 逐个导入，修后正好 41 / 17 |
| `report` 的 Claude 用量虚高 | frankie-vps 的日志 203 行 assistant 只对应 69 个 `message.id`，重复行 usage 完全相同；CC Switch 记为 `session:<message.id>` | 按 `message.id`（Codex 按 `response_id`）去重，跨主机共享去重集 |
| 配了 `RemoteCommand` 的主机永远连不上 | macbookpro：`Cannot execute command-line and remote command.` | `-T -o RemoteCommand=none` |
| macOS 远端探测永远 0 个文件 | BSD `wc -l` 输出 `       2`，拼成 `codex=       2` 后按空白切开解析成 0；`du -sh` 同理 | `$((c))`、`awk '{print $1}'`；顺带把 `-newermt '-3 days'` 换成 POSIX 的 `-mtime -3`（BusyBox 没有 `-newermt`） |
| 修好 macOS 后，同一台 Mac mini 会被同步三遍 | `macmini` / `macmini-lan` / `macmini-tailscale` 指向同一台机器 | 探测时输出近 3 天会话文件路径的 cksum 作指纹，同指纹只留一个；与本机指纹相同的跳过 |
| 失败原因只有 `ssh 退出码 255` | 拉取时 ssh 的 stderr 被丢弃；失败后再探测一次又成功，于是连 probe 的原因都没有 | 单独线程收 stderr、附最后一行；去掉多余的二次探测 |
| 定时任务的 `--hosts` 绕过退避 | `REMOTE_USAGE_HOSTS` 被当成命令行点名 | 只有命令行点名才无视冷却 |
| 全部探测失败时退避不累计 | `probe_candidates` 记了失败，随后 `bail!` 早于 `save_state` | 探测后立即落盘；"全部冷却 / 没有可同步主机"不再当错误 |
| 首次失败实际要等 30 分钟才重试 | 失败时刻比本轮开始晚几秒，下一轮恰好差几秒还在冷却 | 冷却判定留 60 秒余量 |
| 文档写着「5 天自动清理」，代码里没有 | 镜像已 270MB 且只增不减 | `mirror::prune`，`retain_days` 默认 7（与 report 默认窗口一致），导入之后才清理 |
| 手动同步与定时任务可能撞车 | 无锁；state.json 直接覆盖写；配置写坏会被静默忽略，`--set-*` 时还会被默认值整个覆盖 | `sync.lock`（`File::try_lock`）、原子写、每台落盘、配置解析失败时明确提示 / 拒绝覆盖 |

### 一处更正

最初以为 macOS 的 find 不认 `-newermt '-3 days'`，复核发现那是 Claude Code 的 shell 把 `find`
包成了 bfs；`/usr/bin/find` 其实支持。macOS 远端真正的问题是 `wc -l` / `du -sh` 的前导空格。

### 关于 255

两台主机的 255 都发生在本机睡眠前后（两次同步之间空了约 80 分钟，第二台的拉取持续了 7 分钟才失败），
失败后立即重新探测又是通的。推测是 DarkWake / 合盖打断了传输。修复后错误里会带 ssh 的原话
（如 `Timeout, server … not responding.`），下次能直接确认。

### 独立评审后的补充（同日）

另起一个评审 agent 逐项复核（含 bash-as-sh / dash / zsh 下跑两段远端脚本），无 CRITICAL / HIGH，按 MEDIUM / LOW 修了：

| 问题 | 处理 |
|---|---|
| `config.json` 写坏时按默认值（保留 7 天）清理，可能违背用户的 `retain_days: 0` | 解析失败的一轮不清理 |
| 配置文件里的主机名没走校验（`-oProxyCommand=…` 能传给 ssh） | 主机确定后统一 `check_hosts`，不管来源 |
| 全部探测失败时定时任务静默退出 0 | 以非零退出码报错，带上首个原因 |
| `deferredFiles` 被忽略 | 作为导入提示显示 |
| 本机指纹只取一次，探测期间新建会话就认不出本机 | 探测前后各取一次，任一相同即视为本机 |
| GNU tar 读文件时被追加返回 1，整台算失败 | 远端脚本把 tar 的 1 当成功，放开 tar 的 stderr |
| 交互多选、`hosts --probe` 期间占着锁，定时任务整轮被跳过 | 交互期间释放锁；probe 只在落盘时拿锁并合并最新状态 |
| 传输没有总时长上限，卡死的远端会一直占锁 | 单个目录 60 分钟看门狗 |
| 会话目录是符号链接时探测数到 0 | `find -H` / `du -H` |
| 登录 shell 是 fish / csh 时脚本语法错误 | `ssh host sh -s`，脚本走 stdin |
| plist 里主机名 / 路径未转义 | XML 转义 |
| 空归档测试只看退出码（bsdtar 对空输入也返回 0）、`-mmin` 回退从没跑过、`cmd_sync` 流程没有测试 | 校验 gzip 魔数；假 `find` 强制走回退；`tests/cli.rs` 用假 ssh / cc-switch 跑真二进制 |

评审提出的开放问题（父会话被清理后子代理会话会不会永远暂缓导入）核实后确认是真实形态：netcup 41 个
rollout 里 37 个、nuyek-yeats 17 个里 16 个是子代理会话，父会话都在镜像里、`deferredFiles` 为 0。
清理时已改为保留在用会话的整条父会话链。

端到端测试换成旧二进制跑 7 个全挂，说明它们确实测到了这次的改动。

### 复核（第二轮评审）

评审确认上面 6 个 MEDIUM 修复正确、无回归（并独立核实 `proxy_request_logs.request_id` 为
`TEXT PRIMARY KEY`，别名重复镜像不会重复计数），结论 APPROVE。剩余 LOW 中处理了：

- **bsdtar 的退出码 1 是真错误**（读不了 / 消失的文件被跳过），只有 GNU tar 的 1 才是
  "file changed as we read it"。远端脚本改为先看 `tar --version` 再决定。两台在用服务器都是 GNU tar 1.35。
- 暂缓导入的提示排在最前，最多显示 3 条导入提示，其余只给条数。
- 看门狗到点时 ssh 恰好已自己退出，不再误报成超时；探测（2 分钟）与 cc-switch 导入（15 分钟）也加了上限。
- 清理时只为 `codex/sessions` 读首行找父会话。
- 测试：首次回溯窗口的断言换成 4 天前的文件（在 days 之外、保留期之内），之前那份 200 天的
  文件即使被错拉也会被清理掉，断言永远成立；符号链接体积的断言改为排除 `0B`（BSD du 不加 -H 的输出）。
  两处都做了变异验证：故意改坏代码后测试确实会挂。端到端测试放了假的 `cc-fleet`，不再调本机的 Fleet.app。

### 已知局限（新增）

- 父会话**已经被清理之后**才出现的 fork（如对一周前的会话执行 `codex fork`）：父会话没再更新就不会被
  重新拉回，CC Switch 会一直暂缓导入它；同步结果里会出现「N 个文件被暂缓导入」的提示。
- 本机指纹在探测前后都对不上的极端情况下，本机别名会被同步一次：看板不受影响（按记录去重），
  但 `ccr report` 里会多出这一台，直到镜像过期。
- 看门狗按 pid 发信号：计时恰好在进程退出与解除之间到点、且 pid 已被复用时会误杀，窗口为微秒级，可忽略。

## 10. v0.3.1：传输停滞把整轮同步拖死（2026-10-23）

### 现象

`ccr status` 里 nuyek-yeats 的「上次成功同步」停在 20:38，之后再没有新导入，而主机本身
一直在线（ssh 通、Codex 在跑、远端 `find` 只要 0.24 秒）。查下来是 21:17 那轮同步卡住：

```
ssh  nuyek-yeats sh -s          36 分钟，CPU 0.38 秒
tar  xzf - -C .../.extra-codex-XXX   36 分钟，CPU 0.33 秒
```

本地两个进程都在 sleep、20 秒内文件数 0 增长；远端却已经找不到 tar / find / `sh -s`，
只剩一个 sshd 会话挂在 `do_sys_poll`。远端会话的全部 fd 只有 socket 和 /dev/null，
**管道早就关了，ssh 却没收到 EOF**——这就是「管道半死」：远端命令被杀掉后，ssh 通道
不会正常关闭。

### 为什么拖垮的是整轮

同步是逐台串行的（`main.rs` 的主机循环），整轮还一直占着 `sync.lock`。一台主机卡住
→ 后面的主机排不上 → 定时任务每轮都因为「另一个 ccr sync 正在运行」直接跳过。
所以症状不是「这台机器没数据」，而是「所有机器都没数据」。

### 为什么已有看门狗没挡住

`Watchdog` 只管**总时长**（单个目录传输 60 分钟），而且判定依据是「子进程还在不在」；
而 ServerAlive 只探测连接活不活——连接确实还活着（sshd 会话在），远端命令却已经死了。
两者都发现不了「字节流停住了」这件事。

### 修法

1. **插一层泵**：ssh stdout → tar stdin 之间加一个转发线程，边转发边数字节。
   直接把 ssh 的 stdout 当 tar 的 stdin 是拿不到「有没有新数据」这个信号的。
2. **停滞判定**：传输中超过 10 分钟没有新字节、或 15 分钟没等到第一个字节，就 kill ssh
   并把本轮记为失败（进退避），错误信息写明是停滞。
   首个字节单独设上限，是因为远端 `find` 扫大目录树期间本来就一个字节都没有。
3. **清理残留**：上一轮被杀留下的 `.extra-codex-*` 暂存目录（一次几十 MB）在下轮开始时清掉。
4. 阈值可用 `CCR_TRANSFER_IDLE_SECS` / `CCR_TRANSFER_STARTUP_SECS` 覆盖，端到端测试靠它把
   等待时间压到秒级。

### 验证

- 端到端测试里假 ssh 吐半个 gzip 头就卡住：修复前测试会挂死，修复后 2 秒内自己收场，
  报「传输停滞」，并把失败写进 state（断点不推进、进退避）。
- 真实机器上重跑：暂存目录从 8MB 涨到 30MB 持续推进，同步正常完成。

### 顺带查清的两件事

- 远端 `find` 扫 12GB 的 projects 树只要 0.24 秒，**慢的不是扫描**；
- 那 42 个会话文件总共才 78MB，传输量也不大。**慢的是"传着传着断了"这件事本身**，
  所以要治的是停滞检测，不是传输速度。
